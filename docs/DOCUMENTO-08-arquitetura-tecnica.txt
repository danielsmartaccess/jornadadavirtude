# 1. APRESENTAÇÃO

Este documento estabelece a arquitetura técnica e o modelo de dados da plataforma Jornada da Virtude, considerando a decisão tecnológica de desenvolver a aplicação com React, Vite, TypeScript e Tailwind CSS.

A arquitetura deverá proporcionar uma base modular, tipada, testável e evolutiva, permitindo ampliar as funcionalidades sem comprometer a integridade do sistema.

A proposta preserva os princípios conceituais e funcionais definidos nos Documentos Oficiais anteriores, atualizando sua tradução técnica.

## 1.1. Objetivo técnico

Construir uma aplicação web moderna, modular e sustentável, capaz de suportar:

- Gerenciamento de jornadas.
- Catálogo de virtudes.
- Relação com as sete dimensões humanas.
- Investigação e autoconhecimento.
- Catálogo e acompanhamento de exercícios.
- Diário pessoal.
- Revisões periódicas e finais.
- Conselho de Sabedoria.
- Histórico de jornadas.
- Relatórios e exportações.
- Integrações futuras com backend e inteligência artificial.

## 1.2. Princípio arquitetural

**A interface deverá apresentar a experiência; o domínio deverá preservar as regras; a infraestrutura deverá resolver os detalhes técnicos.**

A utilização de React não deverá concentrar todas as responsabilidades dentro dos componentes.

## 1.3. Decisão tecnológica registrada

| Tecnologia | Responsabilidade | Situação |
|---|---|---|
| React | Construção da interface e componentes | Aprovada |
| Vite | Ambiente de desenvolvimento e build | Aprovada |
| TypeScript | Tipagem estática e segurança estrutural | Aprovada |
| Tailwind CSS | Estilização e sistema visual | Aprovada |
| IndexedDB | Persistência local estruturada | A avaliar |
| Supabase | Backend, PostgreSQL e autenticação | Futuro |
| Vitest | Testes unitários e de componentes | Recomendado |
| React Testing Library | Testes de interação da interface | Recomendado |
| Playwright | Testes ponta a ponta | Recomendado |

A stack principal está definida. As tecnologias complementares serão adotadas conforme a necessidade funcional e técnica.

## 2.1. O que não será feito inicialmente

Não se recomenda:

- Criar microsserviços.
- Adotar Redux sem necessidade demonstrada.
- Introduzir múltiplos frameworks de interface.
- Criar um backend antes de validar os fluxos essenciais.
- Implementar agentes independentes para cada pensador.
- Misturar regras de domínio com componentes React.
- Criar abstrações genéricas sem necessidade real.
- Introduzir bibliotecas apenas por popularidade.

A arquitetura deverá ser proporcional à complexidade efetiva do produto.

│                                             │

│ Coordenação dos fluxos                      │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│                CAMADA DE DOMÍNIO             │
│                                             │

## 3.2. Camada de apresentação

Tecnologias:
- React.
- TypeScript.
- Tailwind CSS.

Responsabilidades:
- Renderizar páginas.
- Organizar componentes.
- Controlar interações.
- Apresentar formulários.
- Gerenciar estados visuais.
- Executar navegação.
- Exibir mensagens de feedback.

Os componentes deverão ser preferencialmente pequenos, reutilizáveis e focados em uma responsabilidade.

## 3.3. Camada de aplicação

Responsável por executar os casos de uso.

Exemplos:
- CreateJourney.
- StartJourney.
- SelectPrimaryVirtue.
- CreateInvestigation.
- CreateDiaryEntry.
- RecommendExercise.
- CreateReview.
- CompleteJourney.

Essa camada coordena as operações e chama os serviços de domínio e os repositórios.

Não deverá depender de componentes React.

## 3.4. Camada de domínio

Representa o núcleo do produto.

Deverá conter:
- Entidades.
- Tipos.
- Estados.
- Regras de negócio.
- Validações.
- Serviços de domínio.

Exemplo:

Uma jornada concluída não poderá ser retomada automaticamente.

Essa regra deverá funcionar independentemente de a aplicação utilizar React, IndexedDB ou Supabase.

## 3.5. Camada de infraestrutura

Responsável pelos detalhes tecnológicos.

Exemplos:
- Persistência local.
- Comunicação com APIs.
- Integração com Supabase.
- Exportação JSON.
- Importação de dados.
- Integração com serviços de IA.

Os detalhes de infraestrutura deverão permanecer isolados das regras de negócio.

## 5.2. Regras de organização

1. Cada feature deverá concentrar os elementos relacionados à sua funcionalidade.
2. Componentes compartilhados deverão permanecer em `components`.
3. Regras centrais deverão permanecer em `domain`.
4. Casos de uso deverão permanecer em `application`.
5. Implementações de persistência deverão permanecer em `infrastructure`.
6. Tipos compartilhados deverão possuir localização explícita.
7. Módulos não deverão acessar diretamente os arquivos internos de outros módulos.
8. As dependências deverão ser direcionadas para abstrações.

A estrutura é uma referência inicial. Não se recomenda criar diretórios vazios ou camadas sem necessidade funcional.

# 6. PADRÃO DE COMPONENTES REACT

## 6.1. Componentes de interface

Deverão ser utilizados para representar elementos visuais.

Exemplos:
- VirtueCard.
- JourneyProgress.
- DiaryEntryCard.
- ExerciseCard.
- ReviewPanel.
- CouncilContributionCard.

Responsabilidades:
- Receber propriedades.
- Apresentar dados.
- Emitir eventos.
- Manter estado visual local quando necessário.

Não deverão implementar regras complexas de domínio.

## 6.2. Hooks

Hooks personalizados poderão encapsular lógica reutilizável de interface e integração com casos de uso.

Exemplos:
- `useJourney`.
- `useVirtues`.
- `useDiary`.
- `useReviews`.

Não deverão ser utilizados para esconder regras de negócio complexas.

## 6.3. Estado global

O estado deverá ser dividido conforme sua finalidade.

| Tipo de estado | Estratégia inicial |
|---|---|
| Estado local de componente | useState |
| Estado compartilhado simples | Context API |
| Dados persistidos | Repositórios e serviços |
| Dados remotos futuros | TanStack Query, se necessário |
| Formulários | React Hook Form, se a complexidade justificar |
| Validação de dados | Zod, recomendado para contratos e entradas |

Não se recomenda instalar Redux antes de demonstrar necessidade concreta.

## 6.4. Navegação

Recomenda-se React Router para:
- Rotas.
- Navegação.
- Parâmetros.
- Rotas protegidas futuras.
- Layouts compartilhados.

A adoção deverá ser compatível com a estrutura do projeto.

# 7. TYPESCRIPT E PADRONIZAÇÃO DE TIPOS

TypeScript será utilizado para reduzir erros estruturais e tornar explícitos os contratos entre módulos.

## 7.1. Regras

- Evitar `any`.
- Preferir tipos explícitos nas fronteiras entre módulos.
- Utilizar interfaces para contratos.
- Utilizar unions discriminadas para estados.
- Utilizar tipos compartilhados para entidades.
- Validar dados externos em tempo de execução.
- Evitar duplicação de tipos.
- Não confundir tipagem estática com validação de dados recebidos.

- Campos em camelCase no TypeScript.
- Campos em snake_case no banco relacional.

## 9.3. Histórico

Registros históricos deverão manter a referência à jornada original.

Alterações de conteúdo conceitual não deverão modificar silenciosamente a memória histórica do usuário.

# 10. ESTRATÉGIA DE PERSISTÊNCIA

## 10.1. Primeira versão

A persistência deverá ser definida conforme a estrutura e a complexidade do MVP.

Recomendação:

- IndexedDB para dados estruturados e operações assíncronas.
- localStorage apenas para preferências simples, como tema e configurações leves.

Essa separação reduz a dependência de armazenamento síncrono para dados mais complexos.

## 10.2. IndexedDB

Poderá armazenar:
- Jornadas.
- Investigações.
- Registros.
- Exercícios.
- Revisões.
- Sessões do Conselho.
- Histórico.

A camada de repositórios deverá abstrair as operações.

Uma biblioteca como Dexie poderá ser avaliada para simplificar o acesso ao IndexedDB, desde que agregue valor suficiente.

## 10.3. Supabase futuro

O Supabase poderá ser adotado para:

- PostgreSQL.
- Autenticação.
- API.
- Sincronização.
- Armazenamento.
- Funções de backend.

A migração deverá ocorrer após estabilização do modelo e dos requisitos de acesso.

# 11. CAMADA DE REPOSITÓRIOS

Os repositórios deverão encapsular a persistência.

Exemplo de contrato:

```typescript
import type { Journey } from "@/domain/entities/journey";

export interface JourneyRepository {
  create(journey: Journey): Promise<void>;
  findById(id: string): Promise<Journey | null>;
  findAll(): Promise<Journey[]>;
  update(journey: Journey): Promise<void>;
  delete(id: string): Promise<void>;
}
```

Implementações possíveis:

- IndexedDBJourneyRepository.
- LocalStorageJourneyRepository.
- SupabaseJourneyRepository.

A aplicação deverá depender do contrato, não da implementação concreta.

## 11.1. Responsabilidades

O repositório deverá:
- Persistir entidades.
- Recuperar registros.
- Atualizar informações.
- Excluir quando permitido.
- Tratar falhas técnicas.
- Preservar integridade.

As regras sobre encerramento e transições de jornada não pertencem ao repositório.

- Restringir registros por proprietário.

# 17. ESTRATÉGIA DE INTEGRAÇÃO COM INTELIGÊNCIA ARTIFICIAL

O Conselho deverá ser um subsistema independente.

Arquitetura proposta:

```text
React Interface
      │
      ▼
Council Use Case
      │
      ▼
Council Orchestrator
      │
      ├── Seleção de perspectivas
      │
      ├── Recuperação de fontes
      │
      ├── Organização das contribuições
      │
      └── Síntese
              │
              ▼
       AI Provider Adapter
              │
              ▼
       Serviço externo de IA
```

A aplicação não deverá chamar diretamente o provedor de IA a partir de componentes React.

Credenciais privadas deverão permanecer no backend.

A recuperação de conhecimento deverá utilizar fontes documentadas e critérios de seleção definidos no Documento Oficial 04.

9. O modelo suportar virtudes principais e relacionadas.
10. Os dados possuírem versionamento.
11. Os fluxos principais possuírem testes.
12. A arquitetura permitir substituir a persistência.
13. O Conselho estiver isolado das regras centrais da jornada.
14. A aplicação preservar a privacidade dos registros.

# 21. CONSIDERAÇÕES FINAIS

A adoção de React, Vite, TypeScript e Tailwind CSS representa a definição da base tecnológica da Jornada da Virtude.

O sistema deverá crescer sem perder sua identidade.

A interface organiza a experiência.
O domínio preserva os princípios.
Os dados preservam a memória.
Os serviços conectam as funcionalidades.
A tecnologia sustenta o desenvolvimento.

**A arquitetura deverá ser suficientemente sólida para crescer e suficientemente simples para continuar compreensível.**
